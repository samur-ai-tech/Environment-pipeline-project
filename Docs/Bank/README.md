The normal order for a new kit is **classify the kit → record its measurements → prepare and validate → reuse native assets or import missing assets → connect → verify retained output**. A new kit supplies its own measurements and construction semantics; it reuses the common rules.

## Begin a task

1. Name the model or kit by its source identity, exact source path and revision/hash. Check whether it or a derivative already exists.
2. Choose the supported route in [Model and modular workflow](MODULAR_WORKFLOW.md). A complete mesh, fixed reconstruction and repeatable wall kit have different contracts.
3. Record the current native table/readback and the target area's profile, HDA and registry from [Files and bank state](FILES_AND_STATE.md).
4. Fill the adaptation record in the modular guide. Reuse the existing converter/importer/validator that fits that route; treat dated batch scripts as examples until their inputs and current baseline are reconciled.
5. Name the writable scope, target area/map, required capability, permitted fallback and completion evidence. Confirm that its consumer and area authorization support the request. Native operations use the existing assignment and editor ownership process.

For a new chat, give it this page, the source identity/path, the intended capability and the required deliverable. The common rules do not need to be rewritten into every brief.

## Bank completion priorities

Use the existing per-item audit queues linked in [Files and state](FILES_AND_STATE.md#current-evidence-and-open-work); do not start another blanket inventory. The recommended order is:

1. Define the intended area and capability, applicable models/families, allowed fallback and evidence of completion.
2. Close the active models' contact/facing evidence gaps, starting with those required by that output. Qualify actual native output through the retained operation, including named save, fresh reopen and ordinary replacement where saved environment delivery is requested. Finish the chosen kit's declared capability before starting another.
3. Add the next required coverage: implement missing placement/assembly/host support, obtain applicable area admission, then publish and qualify its bindings. Bring an exact prerequisite ahead of step 2 when it blocks the chosen target; non-Gaza family permission is one such case. Preserve holds.
4. Complete intake/publication tooling only where the next delivery requires it. Repair inactive helpers/candidates when their route is needed; their defects do not automatically outrank active output gaps.

The enabled rows are the first tranche, not a completion cap. This order names no new target map, releases no hold and activates no repair or generation by itself.
